# Docs & the tag vault

## What it is

The group's documents, filed the way a Parachute or Obsidian vault files
notes — by **nested tags**, not folders. A document is a markdown-bodied
resource whose location is an array of slash-paths (`work/projects/rivr`), so the
same document appears under **every** tag path it carries. There is no
"Documents vs. Tags" toggle: the vault *is* the docs module.

Tag semantics match Parachute exactly (lower-cased slash paths), so a
Parachute/Obsidian vault maps across losslessly.

<Callout type="note" title="Two doc surfaces, and they differ">
  The <strong>Documents tab</strong> on the group page
  (<code>/groups/&lt;id&gt;?tab=documents</code>) is the full vault: tag rail on
  the left, filtered list or the open document on the right. The standalone page
  at <code>/groups/&lt;id&gt;/docs</code> is a simpler surface — the same document
  list and viewer, without the tag rail. There is no
  <code>/families/&lt;id&gt;/docs</code> or <code>/rings/&lt;id&gt;/docs</code>;
  those routes do not exist here.
</Callout>

## How to browse the vault

1. Open the group page and choose the **Docs** tab
   (`/groups/<id>?tab=documents`). It is **members**-visible by default.
2. The left rail shows the tag tree: **All docs**, collapsible facet folders with
   a doc count on each node, and a synthetic **Untagged** bucket.
3. Click a folder **name** to filter the list to that facet. **All docs** clears
   the filter; **Untagged** selects documents carrying no tags.
4. Click a document **leaf** in the rail — or a card in the list — to open the
   viewer.

## How to create and tag a document

1. From the Docs tab, create a new document. It opens at
   `<docsPath>?doc=<id>`.
2. Click **Edit**.
3. Set the title, description, and category.
4. In the **Tags** field, type a slash path — `work/projects/rivr` — and press
   Enter or comma to commit it. Autocomplete offers every existing path in the
   vault **and each of its prefixes** (`work`, `work/projects`,
   `work/projects/rivr`), so nested facets stay consistent.
5. Remove a tag with the **×** on its chip.
6. Optionally tick **Show on About page**.
7. **Save.** Tags persist to `metadata.facetedTags` with a mirror to the flat
   `tags` array in a single update, through the same `updateResource` action the
   viewer already uses — so the same gate applies.

## Good to know

- **Tags are an index, not a location.** A document under three tag paths is one
  resource, not three copies. Retagging never moves or duplicates the underlying
  row.
- **Membership gates the tree.** The rail's data comes from
  `GET /api/agent-hq/faceted-fs?groupId=…`, which lists documents owned by the
  group agent and gates on group membership — server-side, from the session, not
  from the client.
- **Tag edits are gated to the document's owner/author**, the same enforcement
  the viewer already applies to any edit.
- A document can be surfaced on the group's **About** page with the
  "Show on About page" checkbox.
- **There is no per-document sharing control in the viewer.** Who can see a
  document follows from its owner and the group-membership gate above, not from
  a share action.

## Access control (engine present, no UI here)

This instance carries the full permissions engine used across RIVR:

- **`check(actorId, verb, targetId, targetType)`** — the single authorization
  entry point, with `canView` / `canManage` / `canUse` shorthands.
- **Direct grants** — `grantPermission` / `revokePermission`.
- **ABAC policies** — `createPermissionPolicy`, `getPoliciesForTarget`,
  `deletePermissionPolicy`, with allow/deny rules over attribute conditions
  (`ATTRIBUTE_OPERATORS`) and a protected set of system-controlled attribute keys.
- **Per-resource paid access (x402)** — `GET /api/resources/[id]/access` is the
  one gated endpoint implementing the verified-principal model. A verified
  principal with a grant is served. **x402 is off for every resource by
  default**; when it is off and the caller has no grant, the answer is a plain
  403 — there is no paying your way in. Where an owner opted a record in, a
  caller with no grant gets a **402** plus payment requirements, and after
  facilitator verify + on-chain settle is served with an idempotent receipt
  persisted. An authenticated payer who already holds a receipt is re-granted
  without being charged again.

<Callout type="warning" title="Honest limitation">
  There is <strong>no ACL panel in this app's UI</strong> — no visibility picker,
  grant editor, ABAC policy builder, or x402 opt-in control on the document
  surface. The engine above is reachable from server code and the gated access
  endpoint; the authoring UI for it is not part of this build. Earlier docs
  described that panel in detail. It isn't here.
</Callout>
