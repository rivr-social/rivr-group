# Admin (there is no admin console)

## What it is

**There are no `/admin/*` pages on this instance.** An earlier version of this
wiki listed an admin dashboard, user manager, task queue, graph explorer, and
badge admin. None of those routes exist in this codebase — they were inherited
from the global hub's docs.

Running this instance is split three ways:

- **Group administration** happens on the group itself — the Settings page and
  the admin-only controls embedded in each group tab. See
  [Groups & subgroups](/docs/wiki/groups).
- **Instance ownership** has exactly two dedicated pages: outgoing email and
  federated-visitor access.
- **Everything else** — badge issuance, job attestation, treasury moves,
  governance settings — is done inline on the surface it belongs to, by whoever
  holds authority there.

## How to reach the real owner surfaces

1. Sign in as an instance admin (an agent flagged admin in its metadata; for
   visitor-access, the instance **owner** specifically).
2. Open **`/settings/outgoing-email`** to set this instance's transactional SMTP
   credentials, send a test message, or delete the config and fall back to the
   shared relay. Non-admins are redirected back to `/settings`.
3. Open **`/settings/visitor-access`** to set the policy for federated visitors
   landing here from another RIVR instance — which capabilities a visitor is
   granted and how long their session lasts — and to review the recent-landings
   log (referral path, home instance, granted scope).

## Good to know

- These two pages are the only owner-scoped pages on the instance. If you were
  told to "open the admin panel", you want the group's
  [settings tabs](/docs/wiki/groups#how-to-change-a-group-setting) instead.
- The SMTP form deliberately does **not** expose federated-auth email routing —
  that is pinned by the mailer so a peer admin cannot redirect authentication
  mail. The UI says so inline.
- Group admin authority **cascades**: an admin of a parent org administers its
  subgroups (`isGroupAdminCascade`). There is no separate "platform admin" role
  with a UI here.
- The page-level redirect is a convenience, not the security boundary — each API
  route re-checks authority server-side.

## Under the hood

| Surface | Route | Source |
| --- | --- | --- |
| Outgoing email | `/settings/outgoing-email` | `src/app/settings/outgoing-email/page.tsx` |
| Visitor access | `/settings/visitor-access` | `src/app/settings/visitor-access/page.tsx` |
| SMTP config API | `/api/admin/smtp-config`, `/api/admin/smtp-config/test` | `src/app/api/admin/smtp-config/**` |
| Visitor-access API | `/api/admin/visitor-access` | `src/app/api/admin/visitor-access/route.ts` |

Those three route files are the **entire** `src/app/api/admin` tree.
