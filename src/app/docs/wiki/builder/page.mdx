# Builder — publish a website

## What it is

A site builder that generates a real static website **from content you already
have in RIVR** — the profile, posts, events, and offerings of a person or a
group — and publishes it. No coding. You pick sections and a theme; the server
does the generating.

Published sites are served from this instance at
`/groups/<ownerId>/site`, and can additionally be bound to **your own domain**.

There is also an **AI assistant inside the builder** that can read and edit the
site's files and publish for you.

## How to publish a site

1. Go to **`/builder`** — you build **your own** site by default.
   To build a **group's** site, use `/builder?group=<groupId>` (you must have
   write access on that group), or go to
   `/groups/<id>/settings` → **Site** → **Open Site Builder**.
2. Tick the **sections** you want included.
3. Pick a **theme** from the presets.
4. Click **Publish**. The version number is confirmed in a toast; the whole
   version history is listed below.
5. Click **View Published Site** (or open `/groups/<id>/site`) to see it live.

## How to connect your own domain

DNS here is **manual** — this instance has no DNS-write connector, so you add the
records yourself.

1. In the builder, scroll to the **custom domain** card. You must have a live
   published version first.
2. Enter your domain.
3. The panel shows the **exact A / CNAME records** to add at your DNS provider.
4. Add them, then click **Verify** — the server performs a real DNS lookup
   against this app's host.
5. Click **Connect**. The binding is persisted, and the middleware's
   host-dispatch begins serving your published snapshot on that domain.
6. **Disconnect** unbinds it.

## How to use the builder assistant

1. In `/builder`, open the **assistant panel**.
2. Ask for a change in plain language — "make the header dark", "add an about
   page".
3. The assistant works on a **working copy** of your site files. Its per-turn
   changed-file chips (e.g. `✎ style.css`) let you see exactly what it touched
   **before** anything goes live.
4. Ask it to publish when you're happy. It will **not** publish unless you
   explicitly ask — the system prompt forbids it.
5. On publish you get a **Published vN** badge and the version history refreshes.

### What the assistant can and cannot touch

It has five tools — `list_files`, `read_file`, `write_file`, `delete_file`,
`publish_site` — inside a jail:

- Paths must be workspace-relative with no dot-leading segments.
- Extensions are allow-listed: `html`, `css`, `js`, `json`, `svg`, `txt`, `xml`.
- Limits: **400 KB per file**, **2 MB per workspace**, **60 files**.
- **`index.html` cannot be deleted.**
- Publishing is an injected callback — the tool module has no database access of
  its own.

For a group, the assistant uses that group's own encrypted Anthropic key when
one is configured (Settings → Assistant), otherwise the instance credential.

## Good to know

- **The owner is never taken from the client.** `/builder` resolves the target
  server-side; `?group=` only *names* a target, and authority is re-verified in
  every `/api/builder/*` action via `resolveSiteOwnerSubject`. Unauthorized
  targets redirect to the group page.
- **Federated owners can use it.** The page resolves the viewer through the
  remote-viewer-aware pair (local session **or** the `rivr_remote_viewer`
  cookie) — a bare `auth()` gate used to lock a federated group admin out of
  their own builder in a login loop.
- **Two publish paths.** The ordinary Publish button **regenerates** the site
  from your RIVR resources. The assistant publishes the **raw edited files** —
  which is why the assistant's edits aren't discarded.
- **A domain can only be bound to one owner** — a second attempt returns
  `DOMAIN_TAKEN`, backstopped by a unique index.
- **Site publications are home-authority and are never federated.**
- Published pages get a minimal per-site CSP; HTML is served with
  `<base href="/">` so a custom domain serves from its root. Web fonts are
  allowed.
- **Operator prerequisite:** for custom domains to work, the instance's Traefik
  needs a catch-all router plus HTTP-01 certificates so unknown Hosts reach the
  container. That's infrastructure, not app config.
- **Known boundary:** the middleware matcher excludes some static extensions, so
  a deep link to a literal `*.html` path on a custom domain bypasses
  host-dispatch. Generated sites link extension-lessly, and css/js pass through
  fine.

## Under the hood

| Surface | Route | Source |
| --- | --- | --- |
| Builder | `/builder` (`?group=<id>`) | `src/app/(main)/builder/{page,builder-client}.tsx` |
| Published site (own host) | `/groups/[id]/site/…` | `src/app/groups/[id]/site/[[...path]]/route.ts` |
| Published site (custom domain) | any bound Host | `src/app/site-host/[[...path]]/route.ts` (via `src/middleware.ts` host-dispatch) |
| Preview / generate | `GET`/`POST /api/builder/site` | `src/app/api/builder/site/route.ts` |
| Publish | `POST /api/builder/publish` | `src/app/api/builder/publish/route.ts` |
| Domain | `GET`/`POST`/`DELETE /api/builder/domain` | `src/app/api/builder/domain/route.ts` |
| Assistant | `POST /api/builder/assistant` | `src/app/api/builder/assistant/route.ts` |

- **Model / service:** `src/lib/builder/site-model.ts`,
  `site-service.ts` (`publishSite`, `publishSiteFiles`, `bindCustomDomain`,
  `unbindCustomDomain`, `setDomainStatus`, `resolveBoundPublicationByHost`).
- **Pure host + serve helpers:** `src/lib/builder/site-host-resolve.ts`
  (`normalizeHost`, `matchPublicationForHost`, `computeDomainVerification`,
  `verifyDomainPointsToApp`) and `site-serve.ts` (`resolveSitePath`,
  `contentTypeFor`, `withSiteBase`). Tests in
  `src/lib/builder/__tests__/site-host-resolve.test.ts`.
- **Assistant toolset:** `src/lib/builder/assistant-tools.ts`
  (`makeBuilderToolset`, `validateSitePath`); tests in
  `src/lib/builder/__tests__/assistant-tools.test.ts`.
- **UI:** `src/components/custom-domain-panel.tsx`,
  `src/components/builder-assistant-panel.tsx`.
- **Schema:** `site_versions` + `site_publications` (domain columns included);
  `site_publications_domain_idx` enforces one-owner-per-domain.
